# Task management

Type: action skill
Purpose: owning the AI-task lifecycle on `/task-mcp` — creating, routing, tracking, and closing tasks for any profile.

Verified against `db/schema.rb` (`ai_tasks`), `app/services/mcp/tools/tasks.rb`, and live registry dump 2026-11-02. task-mcp exposes exactly 8 tools: `ai_tasks`, `get_ai_task`, `create_ai_task`, `update_ai_task`, `delete_ai_task`, `get_ai_task_children`, `get_ai_task_parents`, `ai_task_cost`.

## Field reference (the real ai_tasks schema)

- `description` — the only required field and only free-text body (there is no `title`).
- `project_id` / `room_id` / `topic_id` — scope links; `project_id` always set by convention.
- `task_id` — external/linked identifier; `input_event_entity_id` — originating event/entity id. Preserve both when routing from events.
- Hierarchy: `level` (root = 0), `parent_task_id`, `grand_parent_id` (not `parent_id`/`grandparent_id`).
- People: `adder_profile` (creator), `assigneee_profile` (assignee — three e's).
- Context: `proposed_task_context` (known at creation) and `actual_task_context` (learned while working).
- State: `dispatched` / `finished` are the only flags (no `status`; legacy `added_to_kanban`/`runned`).
- Cost: `token_used`, `usd_used`, `usd_budget`; `token_budget` is NOT writable through task-mcp; `importance` integer ≥ 0.

## Creating

1. Dedupe first: `ai_tasks(project_id, finished=false[, room_id, topic_id])` — reuse an equivalent open task instead of creating.
2. `create_ai_task(description, project_id, [room_id, topic_id, level, parent_task_id, grand_parent_id, adder_profile: "workspace", assigneee_profile, proposed_task_context, input_event_entity_id, task_id, importance, usd_budget], dispatched: false, finished: false, token_used: 0, usd_used: 0)`.
3. Hierarchy: child → `parent_task_id` = parent id, `level` = parent.level + 1, `grand_parent_id` = parent's `parent_task_id`; root → nulls and `level: 0`. Never create children deeper than `level` 3.
4. Never create when the (parent) task budget is exhausted: `usd_used >= usd_budget` (when allocated); `null` budget = no gate.
5. Omit optional fields you don't know — do not invent values.

## Working a task (any profile)

1. `get_ai_task` — confirm exists and not `finished`; never re-open finished tasks, create a follow-up child instead.
2. Start: `update_ai_task(task_id, dispatched: true)` — send ONLY the flag. Verified 2026-11-15 (task 61): passing `assigneee_profile` in the update aborts with `NoMethodError: undefined method 'validate_assignee_profile!'` even when the value is unchanged; the assignee is already set at routing and the echo confirms it.
2b. A re-delivered 'new task <id>' notification for a task already dispatched is deduped against your own footprint (tool_cal_logs entries + the task's `dispatched`/`updated_at`/`description`). Early-exit branch — re-delivery of a task already reading `finished: true` with a complete `actual_task_context`: this is a dispatcher replay, the tell being nonzero `dispatch_attempts` plus a `dispatch_error` (e.g. `Net::ReadTimeout`) on a closed row — the dispatcher's HTTP call timed out AFTER the work landed, so re-running it would duplicate deliverables. The same fields can also sit on a NOT-finished row you are actively working — the inbound delivery to you timed out after you started; it is a transport artifact, never a re-run or re-dispatch signal for the current work. Do zero work-side verification (no gate re-checks, no re-post, no re-raise, never re-open); verify only the close-out footprint chain — the task row itself, its per-step cal-log entries (dispatch, each write, deliverable post, cost-first close), and if the directive was folded into a standing task, that carrier row's `actual_task_context` must contain a fold receipt naming the folded task id. Then emit ONE `create_tool_cal_log` noop-verification row citing the verified log ids and report 're-delivery of closed task, no action'. Correct response otherwise: do NOT re-post the ask to the room (double-pinging the founder) and do NOT re-raise any approval — either finish the in-flight action exactly once, or append a receipt line to `description` ('duplicate notification deduped — this record is the footprint', naming the unblock input already requested). On ANY later re-delivery where the blocked state is already fully on the row — whether via that description receipt or via `actual_task_context` naming the exact unblock input — do not append a second copy, and do not treat the pass as write-free. Verify each gate source specifically: read the approval request's own row (`approval_requests(request_id)` — status pending is the live gate, not just the task text), the room's newest messages (omit `from_message_id` or set it above current max — the pending approval message being the newest reply proves absence), and the target entity's state (topic/row sweep confirming nothing changed). Ladder that trio by footprint: when the prior run's cal-log chain proves the raise complete (approval row + gate-message link + blocked-record entries), later passes need only the approval row read plus footprint confirmation — the row's own status is the gate and room chatter cannot lift it, so skip the message/topic sweeps on a pure still-pending pass. Then make the pass observable with one `create_tool_cal_log` row — `used_tool_name: "noop-verification"`, `target_entity_id` = the task id, `change_log` naming the footprint log range deduped against, one verdict per gate checked, and 'no duplicate writes' — and read the log row back before reporting. 'No state change means no log needed' is the WRONG verdict here: the iron logging rule gates writes, but a dedupe pass against a live human gate is exactly what the audit trail must show. A deliberate no-op must appear in the audit trail, never be silence.
3. Blocked: append the blocker to `description` via `update_ai_task` (no notes/status fields exist). Blocked is never `finished` — leave the task dispatched-open with the exact unblock input named. EXCEPTION — absence-report task: when the directive itself makes reporting the absence the deliverable ("verify first; if it does not exist, report once in <room> and offer to register <intent>"), the report-plus-offer IS the completion: run the same cluster, then close cost-first as `finished` with the deliverable ids and the exact requested inputs named in `actual_task_context` — the human gate then lives in the carrier topic's `required_actions`, not as an open flag on the task. An `offer` never means `create`: a suggested user-visible write (todo, tracker row) waits for the owner's confirmation and belongs to a later pass. When verifying absence, a carrier/record row registered by the routing of the directive itself is NOT proof the artifact exists — only a pre-directive origin counts. Close out the blocked state as a CLUSTER of writes, not just the task: post the blocker message to the task's room → `create_message_topic` linking it (add_message silently drops the topic link, so create it explicitly and re-verify with `search_messages_of_room(room_id, topic_id=<t>)`: the message must appear on the page with that topic in its `topics` array — relink if absent) → `update_topic` state/memory with the sweep evidence and unblock condition (`update_topic` patches only the fields you send and preserves the rest, but long text makes a combined write risky: send `memory` and `state` as two SEQUENTIAL single-field calls, verifying from each response echo that the other field survived, and keeping every `tool_call` under the transport size cap) → `create_room_history_topic` snapshot → `create_tool_cal_log` for every state-changing call including both `update_ai_task` lifecycle writes (dispatch, then blocked-record). The blocked-record and the FOOTPRINT receipt may be ONE call — send `actual_task_context` and the receipt-extended `description` together (dispatch stays a separate first write); log the combined write as its own footprint entry. Roomless variant: when the task's project has no room at all, the room-post half of the cluster is impossible — the combined blocked-record write plus its cal-log row IS the complete footprint; never substitute another project's room or an unrelated room surfaced by `list_rooms`.
4a. A task whose description begins `Gated action:`: load the `bot-approvals` skill BEFORE the first approval raise — the raise tools carry undocumented required arguments (creator identity) and raise-time body rules that live there, not in the schemas or this skill.
4. Gated approval task whose required content has no origin on record: sweep for the origin first (search each candidate room via `search_messages_of_room` with `message_analysis_content_summary`, plus `tool_cal_logs`, `project_knowledge_items`, `knowledge_summary_items`), then — if still absent — do NOT draft invented content. Whether to raise approval now depends on what the order demands: (a) if the deliverable itself needs the missing input (e.g. the ADR text to be filed), do NOT raise an approval with nothing to approve — post the blocker plus exact input needed to the task's room, record it in `actual_task_context`, and wait. (b) if the description explicitly orders "first raise approval via add_approve_request_with_message", the approvable content IS the execution plan: raise it with `body` naming the concrete actions, the gates (which inputs are missing and who must supply each), and what will NOT run until resolution — the approval message then doubles as the room blocker post, so skip a separate add_message; (c) if the origin sweep finds the PROJECT itself empty (no description, members, room, knowledge, tracker rows), the approvable content is a purely procedural setup scaffold grounded only in platform facts on record (current phase, active status-period end date), with domain scope explicitly gated on the creator's intent — never invented goals or dates. Either way the task stays dispatched-open and the approval gate is satisfied only after approval AND real source content arrive.
5. Child tasks: re-validate parent via `get_ai_task_parents` before deep work.
5b. A directive that owes a live sibling task an input but forbids deciding or closing that sibling's gate: deliver the input as a RECEIPT line appended to the sibling's `actual_task_context` — the update REPLACES the field, so resend the old text plus the append — give the write its own cal-log entry, and never touch the sibling's description or lifecycle flags for it.
6. Finish: FIRST `ai_task_cost(task_id, token_used, usd_used)` — it writes the costs and rolls deltas up to every ancestor; then `update_ai_task(task_id, finished: true, actual_task_context: "<what was done/learned, ids touched, verdict if no action>")`.
6a. A task scoped "plan/recommendations for founder review — do NOT execute": the deliverable is the posted plan message itself (verdict first; per item its owner, deadline, gate, and the decisions/inputs owed, named inline). Do not execute, and create NO tracker rows (milestones/todos/status updates) — those user-visible writes stay approval-gated until the founder accepts the plan. Vehicle tasks discovered during the reads keep their existing blockers; re-posting their asks double-pings the founder.

## Update immutability

`update_ai_task` can change only: `description`, `adder_profile`, `assigneee_profile`, `actual_task_context`, `dispatched`, `finished` (+ legacy aliases), `topic_id`, `task_id`, `input_event_entity_id`. Costs move only via `ai_task_cost`. Everything else (`project_id`, `room_id`, `level`, parent links, budgets, `importance`, `token_budget`) is fixed at creation. Validation is strict: one extra key outside the allowed list aborts the WHOLE update with an ArgumentError echoing the allowed keys — send only the keys you intend to change, never a harmless-looking note field.

## Deletion

`delete_ai_task` is for erroneous duplicates you created — never for closing work; closing means finished + cost.

## Pitfalls — sweeps and batched calls

- `search_messages_of_room`: `from_message_id` is an upper bound from which results descend, but its INclusivity has flipped across builds (verified exclusive 2026-11-02; later observed returning N itself when passed N). Never rely on either behavior: pass a value above the message you need (current max id + margin) and confirm the decisive id actually appears in the returned page before concluding absence — a sweep reading a short or empty result as 'no mention exists' then reaches the wrong verdict either way. Conversely, to test whether ANYTHING newer arrived after a known message (e.g. the founder's reply to your ask), omit `from_message_id` entirely and take a small newest-first page — pinning the bound at your own ask hides every later reply and produces a false 'no answer yet' verdict.
- An entity id named in a directive (blocker #, todo #, issue #) may have no row anywhere — a resolved-and-deleted blocker leaves only the founder's one-line directive as its trace. The directive line is not content: include in the exact-input request what the entity's text was and whether its tracker row was deleted on resolve, and re-check the attention/todo tables are genuinely empty rather than filtered by a wrong project/room id.
- A room message claiming a completed action ('Created topic X', 'Filed Y') is a CLAIM, not a row: before treating the claimed entity as a directive's target or planning to update it, verify it actually exists via the entity's own search tool (e.g. `search_topics` by name). If no row exists, make 'the claim is unbacked — does the ask mean to actually create it?' an explicitly named gating input; and if the claimed entity's surrounding thread differs from the directive's subject, state that context mismatch too instead of assuming linkage from proximity.
- A capped listing sweep silently leaves a time gap: the oldest returned message can be far newer than the event whose after-history you are proving empty (the page cutoff lands between the two). Before declaring 'X never landed since event N', re-query with `from_message_id` = lowest id from the previous page and repeat until the window descends to N — the decisive record (a verdict, a lift, a resolution reply) sitting just under the cutoff is otherwise missed and 'no record on file' becomes a false claim.
- Sweep readability: parse a message sweep programmatically into one compact line per message (id, timestamp, creator, analysis id, topic links, body snippet), then dump full bodies ONLY for the cited ids. Verdicts come from the digest, quotes from the targeted full dump — reading raw pages buries the decisive line and invites page-cap mistakes. Large results spill to an archive file; read that file, do not re-request the sweep. When an interpreter path is unavailable (unattended surfaces can decline `execute_code`), analyze the archive itself: `search_files` case-insensitive keyword regex pointed at the spillover directory covers every swept page in one call, then `read_file` targeted windows for the cited messages — same verdict, zero re-requests. When only a few specific rows matter rather than an exhaustive sweep, skip the archive entirely and fetch each by id with the entity's `get_` tool — targeted row reads are cheaper and return full fields.
- An empty `list_ai_profiles` is NOT proof that profiles are unregistered — the read can return zero rows while working profiles exist; verify registration by platform behavior (a profile appearing as `adder_profile`/assignee on live delivered tasks) before making routing decisions that hinge on it.
- `tool_describe` accepts at most 10 names per call — split larger schema loads into two parallel calls instead of losing a round trip to the cap error.
- Sweep filters match less than they appear to: `search_messages_of_room`'s `message_analysis_*` filters match only fields of the ANALYSIS row, so an un-analyzed message is invisible to `message_analysis_content_summary` — pair content-filter searches with a plain descending listing sweep before concluding 'no origin on record'. `tool_cal_logs` accepts no target-entity parameter; a passed unknown filter is silently ignored and the unfiltered recent list comes back — match the footprint yourself client-side before declaring 'no footprint'. Explicit nulls do NOT get that silent-drop treatment: passing `project_id: null` for an optional id parameter fails client-side argument validation ('None is not of type string, integer') and the tool is never invoked — these schemas are anyOf string/integer, not nullable; omit the key entirely. The same silent-drop applies to ACTION tools: `create_tool_cal_log` called with `body` instead of `change_log` SUCCEEDS and persists the row with `change_log: null` — no error surfaces; read back the create echo and use exact schema field names when batch-logging a cluster.
- Batching deferred MCP calls through `tool_call`: parser SIZE cap verified 2026-11-15: even size-1 calls are rejected once the total `calls` JSON passes roughly 2500-2700 chars (error offset lands near the end of the big string; shortening the body moves the offset, proving size, not a stray char). Shape addendum 2026-11-15: pretty-printed `calls` arrays (leading newline after `[`, indented keys) fail with 'Expecting , delimiter' at mid-string offsets even when each entry is small; the identical content resent as compact single-line JSON parses fine — always emit `calls` compact. Safe shapes proven live: keep each `tool_call` under ~2500 chars with flat, single-level strings; for long room messages do small first write + `edit_message` (succeeded at ~2000 chars) or `edit_approval_request` follow-up. Make parallel single-entry invocations the DEFAULT shape for every batch of writes, not a fallback: multi-entry `calls` arrays were rejected far below the size cap (~1200 total chars of four short cal-log entries, citing a phantom parse offset), so the ~2500 figure bounds single-entry size and never licenses batching. Every entry in `calls` must carry its own `name` and `arguments` keys; an array of bare `arguments` objects fails with a misleading 'not valid JSON' parse error that names no field — rebuild the batch per-entry rather than reformatting the text. The batch parser can also fail with "calls[i] requires a 'name'" on an entry that visibly HAS its name — when a long sibling body breaks the batch, the error misattributes; do not add or reorder keys, apply the size-1 rule. A stray brace or delimiter inside a long hand-written body (e.g. a big HTML message) trips the same parse error, but this one cites a character offset — fix at the offset and resend the whole call; when the offset locates no real stray character (common in long strings with typographic punctuation), do not hunt it — resending or reshaping a multi-entry batch reproduces the same error at the same offset, and the size-1 rule is the only safe shape: issue each entry as its OWN single-entry `tool_call` invocation, and since the entries are independent, send those invocations in parallel in one turn rather than paying a round trip each. Also: bridge/meta tools (`tool_describe`, `tool_search`) cannot be nested inside `tool_call` — invoke them as direct tool calls; only deferred MCP tools go through `tool_call`.

## Example — route a follow-up child

```json
{"tool": "create_ai_task", "arguments": {
  "description": "Re-verify ADR-7 scope freeze against reopened item 66",
  "project_id": 2, "parent_task_id": 88, "level": 1, "grand_parent_id": null,
  "adder_profile": "workspace", "assigneee_profile": "coder",
  "proposed_task_context": "all_hands item 66 reopened 2026-11-02; parent task 88 delivered ADR-7",
  "input_event_entity_id": 66, "dispatched": false, "finished": false,
  "token_used": 0, "usd_used": 0, "importance": 3}}
```

Close-out when done:

```json
{"tool": "ai_task_cost", "arguments": {"task_id": 91, "token_used": 24500, "usd_used": 0.19}},
{"tool": "update_ai_task", "arguments": {"task_id": 91, "finished": true,
  "actual_task_context": "ADR-7 still valid; note added to record; blocker 43 left open"}}
```
